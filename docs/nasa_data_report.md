## 2. CRS, одиниці та перевірка оригіналу

DEM — одноканальний Float32 GeoTIFF, 4456 × 5067 пікселів.

- CRS: `Jezero_Crater_Projection`, equirectangular, стандартна паралель **18.4663°**, центральний меридіан 0°.
- Марсіанська сфера: радіус **3 396 190 м**, зворотне стиснення 0.
- Географічні координати: **планетоцентрична широта, східна довгота**.
- Піксель: **20 × 20 проєкційних метрів**, без повороту.
- NoData оригіналу: **−3.4028234663852886e+38**.
- Висоти: метри; USGS описує вертикальне узгодження доданих DEM з MOLA. Нового перетворення вертикального датуму не виконували. Сам TIFF/PDS XML не кодує окремий повністю визначений вертикальний CRS; не приписуємо йому неописану точність.
- Офіційний PDS4 XML підтверджує радіус, напрям довгот, тип широти, піксельний розмір і NoData.

Оптика має іншу equirectangular-проєкцію: стандартна паралель **0°**, той самий радіус Марса, 6 м/піксель, NoData 0. Її **перепроєктовано**, а не просто скопійовано affine DEM.

Геологія: Mars Transverse Mercator, центральний меридіан **77.5°E**, масштаб 1, та сама сфера. Шар геобази: **`GeoUnits_v1`**.

## 5. Метод ухилів і маски

Для висот використано центральні скінченні різниці, на зовнішній межі — односторонні. Ухил:

`degrees(atan(sqrt((dz/dx_ground)^2 + (dz/dy_ground)^2)))`.

Equirectangular-проєкція має масштаб по X, залежний від широти. Для кожного рядка застосовано:

`dx_ground = 20 * cos(latitude) / cos(18.4663°)`.

У межах AOI це приблизно **19.9976–20.0074 м**; по Y — 20 м. A* може користуватися майже квадратною 20-метровою сіткою, а для точних довжин ребер слід використовувати марсіанську відстань з `TerrainCoordinates.distance_m`.

NoData не заповнювали. Якщо для похідної бракує сусідів, клітинка виключається зі спільної маски висот/ухилів. Первинну маску збережено окремо. У поточному обрізанні відсутніх даних немає.

## 6. Геологія та чотири наукові області

`science/points_of_interest.geojson` містить **чотири реальні географічні області**, що відповідає дозволеному ТЗ варіанту «координати або підтверджена географічна область»:

1. **Jezero fan 2 unit** — область віялових відкладів; інтерес: їхня стратиграфія та просторові зв’язки.
2. **Lower etched unit** — картована геологічна одиниця; інтерес: порівняння з сусідніми одиницями за оригінальною картою.
3. **Eolian bedform unit** — еолові форми; інтерес: вітрова переробка поверхні.
4. **Jezero floor unit** — дно Jezero; інтерес: його зв’язок з віяловими відкладами.

Це **не точкові цілі марсохода**. Геометрії походять з `GeoUnits_v1`, обрізані за AOI й об’єднані за первинною назвою. Збережено вихідні FID, назви, символи, атрибути, DOI та URL архіву. Первинні `SHAPE_Area`/`SHAPE_Length` — атрибути вихідних об’єктів, не площі/периметри обрізаних геометрій.

Підтверджених фото конкретних геометрій не додано (`photo_url: null`), щоб не створювати неправдивої прив’язки.

**Важливе обмеження USGS:** SIM 3464 створювали на semi-controlled CTX; карта може мати випадкові зміщення **100–200 м** відносно surface-operations CTX. Геометрії не «підганяли» за зображенням. Масштаб 1:75 000 і зміщення не дозволяють трактувати межі як точні межі дрібних перешкод.

## 9. Інтеграція

### Frontend / Leaflet

Готова конфігурація: `data/processed/imagery_config.json`. Сервер має віддавати PNG за її URL. Для цього невеликого AOI достатньо `L.imageOverlay` без зовнішнього WMTS. GeoJSON координати мають порядок **[lon, lat]**, Leaflet bounds — **[lat, lon]**.

Використовуйте `L.CRS.EPSG4326` **лише як кутову проєкцію відображення** і перевизначте її Earth-distance на сферу Марса. Не показуйте земні тайли, не викликайте земний `LatLng.distanceTo` для метричних результатів; довжини, профілі та маршрути розраховує backend з марсіанською геометрією. GeoJSON тут є контейнером марсіанських координат, **не RFC 7946 WGS84-даними**. Звичайний земний GIS може помилково інтерпретувати ці файли.

Геологічні полігони й наукові області показуйте через `L.geoJSON`; для наукових областей використовуйте polygon/tooltip, не фальшиві точкові маркери. Назви й символи — у `geology_legend.json`.

NASA Trek: https://trek.nasa.gov/tiles/apidoc/trekAPI.html?body=mars перевірено; live WMTS/WMS не є залежністю MVP, бо підготовлено офіційну локальну орторектифіковану CTX-альтернативу.

### GIS, backend та A*

```python
import numpy as np
from scripts.terrain_coordinates import TerrainCoordinates

elevation = np.load("data/processed/jezero_elevation.npy", mmap_mode="r")
slope = np.load("data/processed/jezero_slope.npy", mmap_mode="r")
valid = np.load("data/processed/jezero_valid_mask.npy").astype(bool)
coords = TerrainCoordinates()

# Use actual API input here; this demo uses the centre of the delivered raster.
lon, lat = coords.pixel_to_lonlat(125, 125)
row, col = coords.lonlat_to_pixel(lon, lat)
height_m = float(elevation[row, col]) if valid[row, col] else None

# max_slope_deg is an application model parameter, NOT a NASA safety limit.
max_slope_deg = 15
blocked = ~valid | (slope > max_slope_deg)
edge_length_m = coords.distance_m((125, 125), (125, 126))
```

Для профілю маршруту беріть `elevation[row, col]` кожної клітинки й накопичуйте `distance_m` між сусідніми клітинками. Забороняйте переходи через NoData; при діагональному русі узгодьте заборону зрізання непрохідних кутів з Algorithm Engineer.

Affine у метаданих задає **кут пікселя**: центр `[row,col]` — `affine * (col+0.5,row+0.5)`. Власні функції в `scripts/terrain_coordinates.py` вже враховують це. Висоти/ухили/маски мають однакові індекси.

### Зберігання й Git

Оригінальні завантаження, GeoTIFF та NumPy-файли виключені з Git через `.gitignore`; вони **реально існують локально**. ## 10. HiRISE — завантажений та оброблений локальний фрагмент

Офіційний файл:

https://planetarymaps.usgs.gov/mosaic/mars2020_trn/HiRISE/JEZ_hirise_soc_006_DTM_MOLAtopography_DeltaGeoid_1m_Eqc_latTs0_lon0_blend40.tif

Сервер підтримує HTTP Range. Запитом `bytes=0-262143` отримано HTTP **206** і прочитано заголовок без завантаження **1 839 545 409 байт** усього растра:

- 21 400 × 21 488 пікселів, 1 м/піксель.
- Марсіанська equirectangular-проєкція, стандартна паралель 0°, радіус 3 396 190 м.
- Межі у цій проєкції: `[4577366,1085130,4598766,1106618]`.
- NoData: `−3.4028226550889045e+38`.

Після початкової перевірки заголовка **фактично завантажено й оброблено** фрагмент у районі центру CTX AOI. Зчитано 1002 × 1002 вихідні пікселі, включно з однопіксельним halo для правильних похідних на межі. Значення не перепроєктовували й не інтерполювали.

Це оцінка, не виміряний трафік.

### Покриття і перевірка

- Межі: **77.44235216375607…77.45922276861418°E**, **18.4362813419726…18.453151946830715°N**.
- Площа: 1000 × 1000 **проєкційних** метрів; фактично приблизно **949 × 1000 м** на сфері Марса.
- Валідні **1 000 000 клітинок (100%)**, без заповнення NoData.
- Висоти: **−2584.5393…−2553.4346 м**.
- Ухили: **0…32.99470°**.
- Ухили незалежно перераховані з первинного halo; застосовано `dx_ground=cos(latitude)` м, `dy_ground=1` м. Стандартна паралель HiRISE — 0°, **не 18.4663° CTX DEM**.
- Перевірено вихідні висоти, маски, розміри, affine, SHA-256, координатний round-trip, марсіанські відстані та вкладеність у CTX AOI.
- Зіставлено три локальні значення з повторним читанням віддалених вихідних пікселів — усі збігаються.

Відтворення: `python scripts/process_hirise.py`, потім `python scripts/validate_hirise.py --remote-samples`. Повторний запуск використовує збережене вихідне вікно після перевірки SHA-256. Перезапис raw-вікна для іншого AOI заборонений скриптом: інше отримання потрібно зберігати окремо, а не затерти оригінал.

Для координат застосуйте:

```python
coords = TerrainCoordinates("data/processed/hirise/terrain_metadata.json")
```

**HiRISE лишається окремою high-detail сіткою**, не замінює всю CTX-територію й не зшивається з нею автоматично. Різні масштаби, проєкції та можливі вертикальні зміщення треба врахувати перед майбутнім злиттям. Без згладжування 1-метрові похідні також відображають шум фотограмметричної моделі. Детальність не дорівнює точності чи гарантії безпеки; геологічні межі SIM 3464 не стають метровими.
